Agentic RAG アプリの構造と実行原理

このレポートは、ARag の実装を AI/RAG 初学者にも追えるように、ただし内部原理は専門的に省略せずまとめたものです。 特に query rewrite、retrieve の dense/sparse 検索、rerank、ローカルモデルと外部 LLM の境界を重点的に説明します。

WebNext.js 16, React 19, AI SDK
RAGFastAPI, MinerU, BGE-M3
StoragePostgres, Qdrant, Redis
Default LLMClaude Sonnet 4.5

1. アプリの本質

ARag は「LLM が社内文書を記憶している」アプリではありません。LLM は、必要に応じて検索ツールを呼び出し、 その検索結果だけを根拠として回答します。これが RAG、つまり Retrieval Augmented Generation です。

UploadPDF などをアップロードし、RAG service に転送する。
ParseMinerU が文書を title, text, table, equation, image に分解する。
IndexBGE-M3 で dense/sparse embedding を作り Qdrant に保存する。
Retrieve質問に近い chunk を hybrid search と rerank で選ぶ。
AnswerLLM が chunk を根拠に引用付き日本語回答を生成する。

実装上の中心は、Web 側の runAgent が LLM と tool calling を制御し、RAG 側の FastAPI が検索と文書処理を担当する分担です。

なぜ分けているのか

  • LLM orchestration と UI は TypeScript/Next.js のほうが扱いやすい。
  • PDF 解析、BGE-M3、reranker は Python ML エコシステムのほうが自然。
  • 重い文書処理は worker に逃がし、Web リクエストをブロックしない。
  • 検索処理を FastAPI に閉じることで、Next.js はチャンク候補を受け取って LLM に渡すだけで済む。

ローカルモデルとは何か

BGE-M3、bge-reranker、MinerU は、Docker container 内で Python ライブラリからロードされます。 初回は Hugging Face などから重みを取得し、compose の modelcache:/root/.cache volume に保存されます。 以降はその cache を使うため、毎回ダウンロードするわけではありません。

CPU では DEVICE=cpu、GPU compose では DEVICE=cuda になります。 CUDA の場合、BGE-M3 と reranker は use_fp16=True で動きます。これは GPU メモリと速度に有利です。

実装では PyTorch / tokenizer のスレッド非安全性を避けるため、embedding と reranker の推論を lock で直列化しています。 これは並列リクエスト時の不安定さを防ぐための実務的な防御です。

4. rewrite_query の正体

RAG でいう query rewrite は、ユーザーの質問を検索に向いた自己完結な文に変換する処理です。 例えば 2 ターン目で「それの期限は？」と聞かれた場合、検索クエリとしては 「前回話題にしたアジャイル移行ガイドの提出期限」のように、指示語を解決した文のほうが良く検索できます。

このアプリの現行実装

コード上は src/lib/agent/models.ts に rewrite 用の安価モデルが定義されています。 しかし、現行の src/lib/agent/run.ts では rewrite 用モデルを別途呼んでいません。 実際には、チャット LLM が会話履歴を見たうえで retrieve({ query }) の引数を自分で作ります。

履歴を LLM に渡す

toModelHistory が直近 8 ターンを user/assistant message に変換します。

LLM が tool-call を決める

system prompt は「会話文脈を踏まえて自己完結した検索クエリを組み立ててください」と指示しています。

retrieve の query を rewrite_query として可視化

tool-call の part.input.query を、UI 上の rewrite_query ステップとして表示します。

つまり、このアプリの rewrite_query は「独立した Haiku 呼び出しの結果」ではありません。 「LLM が retrieve ツールに渡した検索語を、ユーザーに見える実行ログとして表示したもの」です。

なぜこの方式なのか

  • Agentic RAG では、LLM が検索するかどうか、何回検索するか、どんな query にするかを動的に判断できる。
  • 独立 rewrite フェーズを固定すると、毎回必ず rewrite する単純 pipeline になりやすい。
  • 現在の方式では、フォローアップ質問でも LLM が履歴を見て retrieve query を直接作れる。
  • UI では rewrite_query として見えるため、ユーザーは「どんな検索語で探したか」を確認できる。

5. Retrieve 内部原理

Retrieve は単なる「DB 検索」ではありません。質問を embedding し、意味検索と語彙検索を並列で行い、 その候補を reranker で再評価してから、周辺 chunk を拡張して返します。

embedBGE-M3 が query から dense 1024 次元と sparse token weight を作る。
dense search意味が近い chunk を Qdrant の cosine 類似度で探す。
sparse search語彙が合う chunk を learned sparse vector で探す。
rerankbge-reranker が query と chunk text のペアを再採点する。
expand採用 chunk の前後 chunk を連結して文脈を補う。

5.1 embed

BGEM3Embedder.embed([query]) が 1 つの query から 2 種類の表現を返します。

  • dense vector: 1024 次元の実数配列。意味的な近さを見る。
  • sparse vector: token id から weight への辞書。語彙一致に近い信号を見る。

BGE-M3 を使う理由は、多言語対応かつ dense/sparse の両方を出せるためです。 日本語 RAG では、意味的な言い換えにも、製品名・部署名・日付のような固有表現にも強くしたいので、この二重表現が効きます。

5.2 dense search

Qdrant collection arag_chunks の named vector dense を使い、cosine distance で検索します。 ここでは「文の意味が近い」chunk が上位に来ます。 

store.dense_search(qv.dense, owner_user_id, candidate_k)

5.3 sparse search

同じ Qdrant collection の sparse vector lexical を使います。 BM25 という名前で UI 表示されていますが、実装上は BGE-M3 learned sparse vector による lexical search です。 古典的 BM25 インデックスを別途持っているわけではありません。 

store.sparse_search(qv.sparse, owner_user_id, candidate_k)

5.4 dense と sparse をなぜ並列実行するのか

dense search と sparse search は互いに独立しているため、ThreadPoolExecutor(max_workers=2) で同時に投げています。 Qdrant への往復が 2 回になりますが、直列ではなく並列なので体感 latency を抑えられます。

5.5 merge は RRF ではなく round-robin

現行コードは Qdrant server-side RRF ではなく、dense 結果と sparse 結果を rank 順に交互に取り、 chunk_id で重複排除します。上限は candidate_k、既定 40 件です。 

dense[0], sparse[0], dense[1], sparse[1], ...
重複 chunk_id は捨てる
candidate_k 件で打ち切る

ここでの merge は最終順位を決めるものではなく、reranker に渡す候補集合を作るための処理です。 最終順位は次の rerank が支配します。

5.6 rerank

BAAI/bge-reranker-v2-m3 は query と候補 chunk text のペアを入力し、 「この chunk は質問に答える根拠としてどれくらい適切か」を 0 から 1 に近い score で返します。 

scores = reranker.score(query, [h["text"] for h in merged])
ranked = sorted(zip(merged, scores), key=lambda x: x[1], reverse=True)[:top_k]

既定では top_k=6 です。つまり最終的に LLM へ渡る主要 chunk は 6 件程度です。

5.7 expand

検索で当たった chunk だけでは、前後の文脈が不足することがあります。 そのため、Postgres の chunks から ordinal - 1, ordinal, ordinal + 1 を取得し、 expanded_text として連結します。

Retrieve は「正しい chunk を探す」処理で、expand は「回答に必要な文脈を足す」処理です。 この 2 つを分けることで、検索精度と回答品質の両方を狙っています。

6. 文書取り込み原理

アップロード直後に embedding まで同期実行すると、Web リクエストが数分止まる可能性があります。 そこで ARag は Redis/arq worker に重い処理を任せます。

ファイル保存

RAG service が /data/uploads に raw file を保存し、documents と ingest_jobs を作成します。

MinerU parse

mineru -p file -o out -d device -b pipeline を実行し、*_content_list.json を読みます。

正規化

MinerU の type を title, text, table, equation, image に変換します。

チャンク化

見出し stack を維持し、文境界と token 概算を使って chunk を作ります。表と数式は atomic に扱います。

Embedding と index

BGE-M3 で chunk を vector 化し、Qdrant に dense と lexical の named vector として保存します。

7. Agentic RAG 実行

固定 RAG pipeline なら「rewrite → retrieve → answer」を毎回同じ順番で実行します。 ARag の現行実装は AI SDK の tool calling を使い、LLM が retrieve と fetch_document を必要に応じて呼びます。

retrieve tool

質問に答えるための関連 chunk を RAG service から取得します。各 chunk は引用番号として CitationRegistry に登録されます。

fetch_document tool

すでに retrieve で得た引用番号 [n] を指定し、その文書の周辺 chunk をさらに取得します。

SSE に流れるイベント

イベント意味UI での表示

8. 引用と source 復元

検索結果は LLM に渡す前に CitationRegistry へ登録されます。 同じ chunk は同じ番号を再利用し、1 ターン内で [1], [2] の番号空間を統一します。 

[1] product-plan.pdf — 2章 > スケジュール
本文...

[2] product-plan.pdf — 3章 > リスク
本文...

完了時には citationMap と sources が作られます。 UI の回答中の [1] をクリックすると、citationMap[1] から source と section を特定し、右パネルで該当 chunk をハイライトします。

DB の citations には document title、chunk id、snippet、page、score が snapshot として保存されます。 これにより、あとからスレッドを開いても引用表示を復元できます。

10. 認証と隔離

  • ユーザーパスワードは @node-rs/argon2 で hash されます。
  • セッションは jose の HS256 JWT を httpOnly cookie に保存します。
  • token_revoked_at により、全デバイスサインアウト後の古い JWT を拒否します。
  • Web から RAG service への内部通信は x-internal-token で保護されます。
  • RAG API は Web が JWT から解決した owner_user_id を受け取り、文書・ジョブ・検索を所有者で絞ります。

11. 現状の限界と読み違えやすい点

  • rewrite_query は独立した rewrite LLM 呼び出しではなく、retrieve tool-call の query 可視化です。
  • UI には Slack、Wiki、GitHub、DB などの scope が見えますが、現状の実検索対象は主にアップロード文書です。
  • bm25_search 表示は厳密な古典 BM25 ではなく、BGE-M3 sparse vector 検索です。
  • dense/sparse fusion は現在 round-robin merge で、Qdrant server-side RRF ではありません。
  • LLM は外部 API です。embedding/reranker/parser はローカル container で動きます。
  • CPU 環境では MinerU と BGE 系モデルが遅く、初回モデル download も重いです。
